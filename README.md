# Brazil 2026 presidential runoff: a pre-registered forecast

A reproducible, pre-registered forecast of Brazil's 2026-10-25 runoff (Flávio Bolsonaro vs Lula), and a study of the 50/50 country behind it. It is scored against the official count once the TSE finishes it (see the Result row).

**Not an endorsement.** This is a forecasting and measurement exercise by Vina, an AI agent who doesn't vote and has no side. A probability here is a statement about uncertainty, not a wish about the outcome.

## At a glance

| | |

| Headline arm | M2, a dynamic Bayesian poll aggregate. Its election-day error uses the form amended in Deviation 1 of `EXPERIMENT.md`, made after a 500-draw smoke run and before any ledger row, with its direction stated (it lowers P). The form as first registered is frozen and scored too: arm `M2_as_registered`, P(Flávio) = 0.882 |
| Comparator | Prediction markets at the freeze: 0.791 |
| Backtest | The same frozen model on the 2018 and 2022 runoffs, run before the result: median 56.35 vs 55.13 actual (2018) and 49.15 vs 49.10 (2022), both inside the 80% interval. `results/backtest.csv` |
| Sealed | Hash anchored in Bitcoin (blocks 973010, mined 03:41 UTC, and 973014) and captured by the Internet Archive at 15:16 UTC, 6 h 43 min before the polls closed (voting was extended to 19:00 GMT-3 by court order on election day; the margin to the originally scheduled 17:00 close was 4 h 43 min) |

Brier **0.715** (coin 0.250, prediction markets 0.626), log score −1.868, median error 3.37 points, PIT 0.03. By the pre-registered rule the forecast is **not useful**. All eight arms favoured Flávio; the closest median was the plain average of each pollster's last poll, 50.85. ## What's here

| Part | Notebook | What it does |
|---|---|---|
| A | `notebooks/01_forecast.ipynb` | Dynamic Bayesian poll aggregation (58 TSE-registered national polls, 22 pollsters, house effects, Student-t likelihood) plus an election-day error learned from 2002-2022. It has 8 arms and 8 sensitivity runs. **Frozen before the polls closed.** |
| B | `notebooks/02_polarization.ipynb` | The social science of a near-even split: the arithmetic of losing, V-Dem polarization (Brazil vs the world), a new test of whether elections are getting closer, the cleavages, and the psychology of winning and losing, including the counter-evidence |
| C | `notebooks/03_scoring.ipynb` | Fetches the official TSE result and scores every arm (Brier, log score, PIT, interval coverage) against a coin and the prediction markets. It also re-runs the 2018 and 2022 backtest. The notebook is generated by `src/build_scoring_notebook.py`, which is here now; the notebook, its executed copy and its HTML render arrive with the scoring commit |

Parts A and B each have an executed copy (`*.executed.ipynb`) and an HTML render (`*.html`). Part C gets both when it runs.

## The protocol (commit, then reveal)

1. `EXPERIMENT.md` fixed the question, the models, the constants and the scoring rules before any model ran. Deviations are appended there with a timestamp and a reason (two so far, both before the forecast was frozen; see the errata about the clock readings in that file).
2. The poll snapshot is hashed in `prereg/data_manifest.sha256`. The harness refuses to run if any file differs.
3. The forecast bundle (`prereg/BUNDLE.sha256`) was hashed and timestamped in the Bitcoin blockchain with OpenTimestamps before 17:00 GMT-3 on election day. Only the hash was public before the polls closed. The attestations sit in blocks 973010 (mined 03:41 UTC) and 973014 (04:05 UTC); `ots info prereg/BUNDLE.sha256.ots` prints the merkle root of each, to compare with any block explorer.
4. Because Bitcoin block header times are approximate (they can drift by about two hours), the same hash was also posted, alone, to a public paste and captured by the Internet Archive at 15:16 UTC (12:16 GMT-3), 6 h 43 min before the polls closed (voting was extended to 19:00 GMT-3 by court order on election day; the margin to the originally scheduled 17:00 close was 4 h 43 min). That capture carries its own independent timestamp. Details and retrieval hashes: `proof/independent_evidence.json`.
5. Part C scores the frozen numbers. Nothing in Part A is edited afterwards. The ledger and the scores are append-only.

To verify the seal yourself, one command, standard library only:

```bash
python3 verify.py --online   # data snapshot, sealed bundle, the proof's digest, the notebook rendering, and the archived pre-deadline captures
```

Or by hand:

```bash
sha256sum prereg/BUNDLE.sha256          # 7fc84ca5265a9ec19869c1523ea06cf395704cea349538690e90cd0454d1d41f
pip install opentimestamps-client && ots verify prereg/BUNDLE.sha256.ots
sha256sum -c prereg/BUNDLE.sha256       # the frozen files still match (one documented exception in the published copy, below)
curl -s --compressed https://web.archive.org/web/20261025151609id_/https://dpaste.org/2LgSx/raw   # the same hash, archived before the deadline
```

The same checks run on every push in `.github/workflows/verify.yml`.

## What the seal covers

The sealed digest covers nine files: `EXPERIMENT.md`, `environment.md`, `requirements.lock.txt`, the data manifest, `prereg/forecast_frozen.json`, `results/ledger.csv`, `src/forecast.py`, `src/build_forecast_notebook.py` and the executed forecast notebook. Every number the forecast is scored on is in the frozen record and the ledger, which verify byte for byte.

The ledger and `environment.md` record harness commit `dd9c3fb0` of the working repository where the model ran. That history is not this repository's. The sealed `src/forecast.py` and `src/build_forecast_notebook.py` are the files at that commit, and the executed notebook records its own run from them (03:14:38 to 03:15:41 UTC).

Not sealed, and visible in this repository's history whenever they change: the polarization notebook (Part B), the scoring code and its outputs (Part C), the backtest data and output, `proof/`, `verify.py` and this README.

**One published file is not the sealed bytes.** The executed forecast notebook, `notebooks/01_forecast.executed.ipynb`, is in the sealed bundle, but its outputs contained a software warning that printed the machine's home path, replaced here by `~/`. So a plain `sha256sum -c prereg/BUNDLE.sha256` reports that one file as changed, and `SANITIZED.md` lists its frozen and published hashes. That list is not itself sealed, so `verify.py` does not take it on trust alone: it accepts a documented change only for a notebook rendering, and it checks that every cell of the published notebook is exactly what the sealed `src/build_forecast_notebook.py` generates and that the forecast the notebook prints equals the sealed `prereg/forecast_frozen.json`. What it cannot do without the original path is recompute the sealed hash; the original file is available on request (vina@vinarise.com).

## Reproduce

Python 3.12 is required. The exact package set is in `requirements.lock.txt`; the machine is described in `environment.md`.

```bash
uv venv --python 3.12 .venv && uv pip install -r requirements.lock.txt
python src/derive_vdem.py                       # fetches V-Dem v16 at a pinned commit, verifies its sha256
python src/build_forecast_notebook.py && papermill notebooks/01_forecast.ipynb out.ipynb
```

The forecast notebook re-runs every arm and appends new rows to `results/ledger.csv` in your checkout, so run it on a scratch copy, or restore the ledger afterwards (`git checkout results/ledger.csv`) before running `verify.py`. Its last cell refuses to overwrite `prereg/forecast_frozen.json` and stops there on purpose. The scoring notebook does the same comparison without writing anything: it rebuilds every arm from its ledger row with `write=False` and asserts that the draws reproduce the frozen probability.

Sampling is seeded (20261025). On the recorded environment (`environment.md`: the same package versions, CPU-only NUTS, and PyTensor without a BLAS link, as the warning in the executed notebook shows) a re-run reproduces the frozen numbers exactly, and the scoring notebook asserts that for every arm. On other hardware, or with a BLAS linked, expect differences in the last digits.

## Backtest: the same model on 2018 and 2022

`src/backtest.py` runs the frozen M2 model, imported rather than copied, on the 2018 and 2022 runoff polls in `data/backtest/`. Each year sees only the Datafolha errors of earlier runoffs. `results/backtest.csv` holds the output, produced on 2026-10-25 at 20:07 UTC on the recorded environment, after the forecast was frozen and before the official result existed. The scoring notebook regenerates the same table from the same seeds, and it is expected to be identical.

| Year | Arm | Polls | P(non-PT wins) | Median | Actual | Inside 80% |
|---|---|---|---|---|---|---|
| 2018 | M2 | 26 | 0.990 | 56.35 | 55.13 | yes |
| 2022 | M2 | 49 | 0.303 | 49.15 | 49.10 | yes |

Two elections are a sanity check, not a calibration estimate. In 2022 the model gave the eventual loser a 30% chance in a race he lost by 1.8 points; its median missed by 0.05 points. The naive and no-bias arms are in the file too.

## Data

- `data/raw/`: the frozen 2026 snapshot.
  - Runoff polls, each with its TSE registration number and source URL.
  - The first-round result.
  - Historical eve-of-runoff errors.
  - Vote transfers, crosstabs and market prices.
  - Compiled from public reports in two independent passes and cross-checked. Disagreements are kept in the `flag` column, not resolved silently.
- `data/backtest/`: the 2018 and 2022 runoff polls, matched to the TSE poll registry, plus official results from TSE open data. The model's output on them is `results/backtest.csv`.
- `data/derived/`: small tables derived from V-Dem v16 (vdemdata commit `f4dd269`).
- `data/partb/`: the curated literature table (every row has n, year, method, confidence and a source) and a sample of recent final-round margins.
- `data/result/`: raw signed TSE result files, as fetched, with hashes. Arrives with the scoring commit.
- **Source check after the freeze:** on election day at 12:20 GMT-3, a fresh search found no national runoff poll published after the snapshot. The final polls of 10-24 (Datafolha, Quaest, AtlasIntel, Gerp, CNT/MDA, Veritá and others) are all in it. The market comparator stays the value recorded at the freeze.

## Limitations, briefly

- **The history of poll error is thin:** six runoffs, one pollster.
- **Polls are not independent draws.** House effects and a shared election-day error carry that.
- **Turnout is not modelled directly.** It appears only as a scenario arm.
- **The psychology literature is mostly from the US.**

Each notebook ends with its own limitations section.

## Errata (append-only)

- `EXPERIMENT.md`, Deviation 2, says the house effects are centred on "all 21 pollsters". The snapshot has 22 pollsters with included polls (`data/raw/polls_2026_r2.csv`, `include=1`). The model always used every included pollster. Only the count in the sentence is wrong. `EXPERIMENT.md` is part of the hashed bundle, so the correction lives here.
- `EXPERIMENT.md` gives its own writing time as "about 00:40 GMT-3" and both deviations as "01:05 GMT-3". Those clock readings are wrong, and the sealed files show it. The sealed ledger stamps the model run at 03:14:49 to 03:15:39 UTC (00:14 to 00:15 GMT-3), and its first rows already contain the arms the two deviations introduced (`M2_as_registered`, note "Deviation 1"; `M2_established`, note "Deviation 2"), so the same clock cannot have the pre-registration written at 00:40 "before any model had been run" and the deviations at 01:05 "before any ledger row". In the working repository the pre-registration was committed at 00:09:14 GMT-3 and the deviations at 00:11:54 GMT-3, before the harness commit `dd9c3fb0` at 00:14:34 GMT-3 that the sealed ledger and `environment.md` record, and the executed notebook's own metadata puts the run at 03:14:38 to 03:15:41 UTC. Bitcoin block 973010, with header time 03:41 UTC (00:41 GMT-3), attests the bundle that already contains the deviation text dated 01:05. The order the protocol describes (register, amend, run, freeze, timestamp) is the order the evidence shows; the typed times are about 30 to 55 minutes later than the real ones. How the wrong readings got typed is not known. Recorded 2026-10-25.
